## 第一部分：原始需求（用户定义，评审不改动本部分）

### 1.1 背景

现有竞品监测能力（`competitors` / `competitor_snapshots` / `competitor_shots` 三张表，见 [2026-07-28 设计](2026-07-28-competitor-live-dossier-design.md)）中，直播间截图目前是**人工上传**：人工打开直播间、手动截图、手动传到 `/competitors` 页面。本需求要把"截图"这一步自动化。

### 1.2 目标

**当追踪的竞品账号开播时，自动截取直播画面并归档**，替代人工截图。具体：

- 检测「是否开播」+ 截一张直播画面图，归档到 `competitor_shots`
- 覆盖账号：现有全部已追踪竞品账号 + 新账号 `nexgen1021`（需先建档）

### 1.3 场次规则（核心业务规则）

**同一场直播只截一张**。若当天该账号下播后又开了新的一场，需再截一张——即必须区分"直播场次"，不能简单按天去重。

### 1.4 截图内容

截图范围 = **整个直播画面容器**。TikTok 播放器上叠加的横幅、礼物飘屏、秀场菜单等都算画面的一部分，不单独裁剪或拼接。用元素级截图，不用整页截图或固定像素坐标。

### 1.5 用户给定的约束

1. **本地 Mac 方案**：跑在用户自己的 Mac 上，`cron`/`launchd` 定时触发；不新建常驻服务器/云端基础设施。
2. **不开无头浏览器访问 TikTok**：此前自动化读竞品主页 bio 撞过滑块验证码，TikTok 对自动化访问的检测是真实风险。改为接**用户手动维护的、已登录、已常开**的浏览器 tab。
3. **人工职责边界**：用户自己负责为每个追踪账号开 tab、常驻对应 `/live` 页面、保持登录（暂停播放的做法经评审修订，见 3.2/R2）。脚本不负责开 tab、登录。
4. **巡检节奏**：每账号每天 **4-6 个时间窗口**，不做 24 小时高频轮询——出于"行为模式不要看起来像机器人"的偏好。
5. **通知策略**：截图成功 → 静默入库，不主动通知（与现有每日指标打点一致）；异常（连不上、找不到 tab、疑似验证码）→ 本地日志 + macOS 系统通知，提醒人工介入。

### 1.6 非目标（明确排除）

- 直播间实时互动数据（弹幕、礼物流水、在线人数曲线等）
- 24 小时无差别高频轮询
- 云端/服务器常驻部署
- 自动打开/维护浏览器 tab 本身（登录等前置动作是人工职责）

### 1.7 数据落库

复用现有模式，**不改 DB schema**：

- 图片上传 `competitor-shots` 存储桶
- 插入 `competitor_shots` 一行（`shot_on` = 当天日期，`tag = 'live_auto'`）
- 写库沿用 `scripts/record-competitor-snapshot.ts` 的 service-role 直连模式（已核实该脚本在 origin/main 存在、表字段与需求一致）

## 第二部分：可行性评审结论（2026-08-16）

**总体结论：有条件可行。** 方案大方向正确——不开无头浏览器、接真实登录浏览器，比之前撞滑块的路线安全一个量级。但原设计有三处问题，须将架构从"零请求纯读"改为"低频真实浏览器刷新"后再进实现计划。

### 2.1 核心前提存疑：静止的 tab 大概率感知不到"开播"（致命，须实测）

- 原设计假设常驻 `/@handle/live` 的 tab 会自己从"未开播"变成"直播画面"。直播状态的实时推送依赖**进入直播间后建立的房间 websocket**——主播没在播时房间不存在，页面没有机制订阅"这个主播何时开播"。
- 若前提不成立，检测开播的唯一出路是**脚本刷新页面**，直接违反原"不产生任何新请求"的约束。
- 连带问题：下播后 TikTok web 有推荐/跳转其他直播间的行为，tab 可能自己漂走，runner 按 URL 匹配不到 tab。

**验证实验（进实现计划前必须做）**：挑一个已追踪账号，开播前把 tab 停在 `/live` 页，等它开播，观察页面是否自动切换。预期：不会。

### 2.2 自相矛盾："手动暂停播放"与"截到直播画面"不能同时成立

- 暂停的 `<video>` 渲染的是暂停那一刻的帧；就算页面知道在播，截出来的也是旧帧或黑屏。
- 要截到当前画面必须**恢复播放 → 拉流缓冲 → 截图 → 再暂停**——脚本驱动的交互 + 新增请求，与"零请求"约束冲突；且恢复播放等于"进房"，触发 2.4 的可见性问题。

### 2.3 风控评估（评审重点）

**好消息**：CDP 读取本身对 TikTok 完全不可见——截图、读 DOM 都发生在本机，不产生网络流量。纯读架构下账号风险确实低。

**但正因为如此，"4-6 个窗口"在纯读架构下是心理安慰**：TikTok 看不到巡检节奏，它看到的是常开 tab 自身的流量（websocket、心跳），那是 24 小时的。窗口调度调节的是一个对方观测不到的东西。

一旦引入页面刷新（见 2.1），窗口才真正成为风控节流阀：

- 窗口语义须绑定到"产生请求的动作"：**每窗口每账号最多刷新 1 次**。不能窗口内每次 launchd 唤醒都刷——一个 30 分钟窗口就是 6-10 次刷新，全天几百次准点访问竞品直播页，模式反而更像机器人。
- **CDP 接入方式**：不要用 Puppeteer/Playwright 的 `connectOverCDP`——默认会调 `Runtime.enable`，这是反爬厂商（DataDome 等）公开已知的检测面，TikTok 的 webmssdk 是否也检测无法确认，没必要赌。建议裸 CDP（`chrome-remote-interface` 或手写 websocket），只用页面 JS 观测不到的域：`Target.getTargets` 找 tab、`DOM.getDocument` / `DOM.getBoxModel` 定位截图区域、`Page.captureScreenshot` 带 clip 截元素——全程不注入页面 JS。
- **熔断升级**：原设计只写"本次窗口跳过"。改为**全局熔断**——任何账号出现验证码，所有账号后续窗口全停，直到人工确认恢复。否则每个窗口都会去戳一次验证码页面，这是风控升级的典型触发路径。

### 2.4 原设计未提的暴露面：主播看得见你（业务暴露，比封号更现实）

- 登录态进直播间会出现在**观众列表**，伴随"xxx 进入直播间"公屏消息，主播端直接可见。
- 常开 tab + 每窗口刷新 = 账号每天数次、长期、准点出现在**所有**竞品直播间。对方运营稍加留意即可发现被监测。
- 对策：用与公司无关联的**专用小号**（要有正常使用历史——全新零行为账号更易撞验证码），并接受该小号可能被风控牺牲。注意 TikTok 有设备/IP 关联能力，小号与主账号长期同 IP 同设备则隔离不彻底，是否进一步隔离取决于对最坏情况的容忍度。

### 2.5 场次去重逻辑在稀疏窗口下不成立

- 原设计的状态跳变法（未播→在播才截）依赖**连续观测**。窗口间隔数小时，"在播→在播"完全可能是两场不同直播（中间下播又开播），会静默漏截——恰好违反 1.3 的场次规则。
- 修法不动 schema：从页面数据读 `room_id`（rehydration JSON 里有）写进**本地状态文件**，按 room_id 去重，不按状态跳变。

### 2.6 工程层面问题（不致命，须写进设计）

- **Chrome 136 起 `--remote-debugging-port` 必须搭配非默认 `--user-data-dir`**。专用实例方向正确，但意味着要在专用 profile 里重新登录 TikTok。
- **Chrome Memory Saver 会冻结/丢弃后台 tab**，丢弃后 CDP 读不到内容。关闭 Memory Saver 或给 tiktok.com 加"始终保持活跃"例外，列入人工前置准备清单。
- **Mac 睡眠即全停**。launchd 唤醒补跑落在窗口外会被 runner 跳过，等于静默漏检。可接受，但须作为已知运营约束写明。
- 常开直播 tab 的聊天区 DOM 无限增长，挂几天内存会涨；把"每天/每几天手动刷一轮 tab"写进人工职责。
- 调试端口对本机所有进程开放，等于把该 profile 的登录态交给本机任何程序。单人 Mac 风险低，记录在案即可。

## 第五部分：2026-08-16 真实环境试跑

环境：pollux 手动启动专用 Chrome（`--user-data-dir=~/.chrome-livewatch --remote-debugging-port=9222`）、登录 TikTok、开了 4 个 `/@handle/live` tab。Claude 通过本机 CDP 连接读取/截图，全程零 TikTok 新请求（除下述主动 reload/开 tab）。产出脚本：`scripts/live-watch/cdp-probe.mjs`（探测/截图）、`scripts/live-watch/record-live-shot.mjs`（入库）。

### 5.1 已跑通（正向结论）

- **全链路可行**：对在播的 `nexgen1021` 完成「CDP 连接 → 激活到前台 → 轮询到 `<video>` → 元素级裁剪截图 → 上传 `competitor-shots` 桶 → 插 `competitor_shots`（tag=`live_auto`）→ 公网 URL 200 可访问 → 归到 `/competitors`」。截图为干净的直播画面容器（无侧栏/评论/观众名）。这张已作为本周 nexgen1021 数据留库。
- **CDP 纯本地读取零风控风险**：读 DOM、截图都在本机，TikTok 侧无流量。这一条评审判断得到确认。
- **裁剪选择器**：直播画面就是 `<video>` 元素（本次实测 877×693），`DOM.getBoxModel` + `Page.captureScreenshot` 带 clip 即可，不需要复杂选择器。修正原设计开放问题 #2 的悲观预期。

### 5.2 实锤的新发现（改变架构，须并入需求）

| # | 发现 | 证据 | 影响 |
| --- | --- | --- | --- |
| F1 | **tab 标题 / `/json/list` 完全不可信** | 3 个 tab 标题都停在「正在直播」，实际 body 已是「直播已结束」 | 状态判断不能用标题，必须看渲染后的 body/画面 |
| F2 | **整页 HTML 字符串匹配不可信** | `endedText`/`captchaHint`/`loginWall` 对正常直播页全部误报——i18n 文案包整个打进了 HTML | 状态信号不能全文正则，须限定到渲染 DOM 元素或直接看截图 |
| F3 | **初始 HTML 的 rehydration JSON 里没有直播状态** | scope 只有 app-context/i18n，无 live-room | 真实状态只在「加载后异步渲染的 DOM + 画面」里 → 必须等 hydrate 完 |
| F4 | **后台 tab 不渲染视频** | 后台开的 nexgen1021 tab 播放器全黑、无 `<video>`；`Target.activateTarget` 到前台后画面才出来 | 硬约束：截图前该 tab 必须是前台可见 tab。多账号不能同时挂后台一起截，须逐个切前台 |
| F5 | **`<video>` 延迟挂载** | 前台后仍需十几秒、多次轮询才等到 `<video>` | 固定等待不可靠，须轮询到 `<video>` 出现为止（已实现 `--wait-for`）|
| F6 | **CDP nodeId 会被后续 `DOM.getDocument` 作废** | 轮询拿的 videoNodeId 到截图时失效，导致裁剪静默回退整页 | 截图前必须用当前 root 重新 querySelector（已修）|

### 5.3 隐私暴露：实锤（对应评审 2.4）

nexgen1021 直播间评论流里出现 **「pollux_yc 已加入」** 公屏播报——即当前登录账号 `pollux_yc`（看起来是主号/实名，非小号）进直播间的动作，被主播和全体观众公开可见。**这直接验证了评审 2.4 的暴露面，且当前用的不是建议的专用小号。** R5（换专用小号）从「建议」升级为「上线前必须」。

### 5.4 R1（静止 tab 感知开播）当前结论

- **live→ended 方向**：会自动翻页。pollux 早先开的在播 tab，主播下播后 body 自动变成「直播已结束 + 推荐直播」——房间 websocket 把结束事件推给了开着的 tab。
- **ended→live 方向（R1 真正要问的）**：尚未直接观测。推断为**不会自动感知**——页面进入 ended 态后房间连接已拆除，新开播没有订阅通道。已留基线：`truecolor1003` 的已结束 tab 未 reload。待其真正重新开播时不 reload 复查即可定论。
- 无论 R1 结论如何，F4（后台不渲染）已经决定：**架构必须是「按窗口逐个把 tab 切前台 + reload + 轮询 + 截图」**，纯静止读取路线不成立。

### 5.5 「能否无人值守自己跑完」的回答

happy path 能自动跑完（今天 nexgen1021 就是脚本+CDP 自动完成的）。但 F1–F6 这些脆弱点意味着**全自动无人值守的可靠性还不够**：需要「逐个切前台 + 轮询就绪 + Claude 看截图做最终 live/ended/验证码判断」。这恰好落在 pollux 接受的**「人在旁边监督的半自动」**档位——出异常（验证码/找不到 tab/画面异常）时全局熔断并喊人。成熟后可把稳定逻辑沉淀为纯脚本再谈无人值守。

### 5.7 截图质量（2026-08-16 追加）

pollux 要求：只截真实直播画面区、静音、1080p/original。已落地到 `cdp-probe.mjs`：

- **精确裁剪**：`<video>` 元素框是 877×693（偏横，带黑边），真实流是 1080×1920 竖屏。改为读 `videoWidth/Height + object-fit/object-position` 算出真实渲染矩形（本次 390×693 居中）再 clip——去黑边、排除多人联播时邻座 video 的漏入。
- **静音**：截图前置 `video.muted=true; volume=0`（此前切前台会外放所有直播间声音）。
- **画质**：TikTok web 默认已 1080p60（`videoWidth=1080` 证实），满足要求；"original" 需点画质齿轮菜单，暂未做。
- **黑屏重试**：`<video>` 挂载 ≠ 帧解码好；按截图字节数（<120KB 视为黑屏/加载圈）最多重试 5 次。
- ⚠️ **检测面权衡**：精裁+静音用了 `Runtime.evaluate`（一次性 JS 读），偏离 R7「纯 CDP 不碰 Runtime」的建议。属功能与隐蔽性的取舍——上线前需 pollux 拍板：要么接受这一次 JS 读，要么退回「纯 CDP + 图像分析裁黑边」（精度略降、静音改点 UI）。
- 两张已存图（zense.jp / nexgen1021）已用 `record-live-shot.mjs --replace` 换成精裁版，旧桶文件已删。

### 5.6 遗留待办（并入实现计划）

- 状态判断改为「限定 DOM 元素 / 看截图」，删除全文正则信号（F1/F2）。
