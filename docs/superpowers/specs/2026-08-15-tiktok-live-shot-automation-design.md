# TikTok 直播开播自动截图归档 —— 设计草案

> 状态：Draft（讨论稿，尚未进入实现计划）
> 日期：2026-08-15
> 关联能力：[竞品监测（Competitor Monitoring）](2026-07-28-competitor-live-dossier-design.md) —— 本设计是在已上线的「团播档案」模块上新增一个自动化采集入口，不新建独立系统。

## 1. 背景与目标

现有竞品监测能力（`competitors` / `competitor_snapshots` / `competitor_shots` 三张表，详见 [2026-07-28 设计](2026-07-28-competitor-live-dossier-design.md)）里，直播间截图目前是**人工上传**——人工打开直播间、手动截图、手动传到 `/competitors` 页面。

本设计要新增的能力：**当追踪的竞品账号开播时，自动截取直播画面并归档**，替代人工截图这一步。范围明确限定为：

- 检测「是否开播」+ 截一张直播画面图，归档到 `competitor_shots`（**不**采集直播间的实时互动数据、弹幕、礼物流水等——那些仍然是非目标）
- 覆盖账号：现有全部已追踪竞品账号 + 新账号 `nexgen1021`（需先建档）

## 2. 关键约束（决定了架构形状）

1. **不做新的常驻服务器/云端基础设施**。这是一个跑在用户自己 Mac 上的本地自动化，用 `cron`/`launchd` 定时触发。
2. **不新开无头浏览器去访问 TikTok**。之前自动化读竞品主页 bio 就撞过滑块验证码——TikTok 对自动化访问的检测是真实存在的风险。为规避这个风险，本设计改为**接到用户手动维护的、已登录、已常开**的浏览器 tab 上读状态/截图，不产生任何新的对 TikTok 的请求。
3. 用户会用自己的 TikTok 账号手动做好前置准备：为每个追踪账号开一个浏览器 tab、常驻在对应 `/live` 页面、保持登录、**手动暂停播放**。这部分是人工职责，不是自动化脚本管的范围。
4. 尽管接常开 tab 之后已经没有额外的网络请求风险，用户仍然希望巡检节奏保留「每账号每天 4-6 个时间窗口」，而不是 24 小时高频轮询——纯粹出于「行为模式不要看起来像机器人」的偏好，不是技术必需。
5. **同一场直播只截一张**；如果当天这个账号下播后又开了一场新的，才需要再截一张（即需要区分"直播场次"，而非简单按天去重）。

## 3. 架构

```
launchd（高频唤醒，如每 3-5 分钟）
   │
   ▼
runner 脚本
   │  读取 config.json：每账号的时间窗口
   │  判断「现在」落在哪些账号的窗口内
   ▼
（仅对落在窗口内的账号）
   │
   ▼
CDP 连接用户常开的专用 Chrome 实例
   │  按 URL 匹配（含 /@{handle}/live）找到对应 tab
   │  不新开 tab、不导航，只读取已有页面
   ▼
状态判断
   │  读当前是否「在播」
   │  和本地状态文件比对上一次检查结果：
   │    未播 → 在播  ⇒ 判定为「新的一场」，触发截图
   │    在播 → 在播  ⇒ 同一场，跳过
   │    在播 → 未播  ⇒ 复位状态，等待下一次跳变
   ▼
截图（命中新场次时）
   │  定位直播画面容器元素截图（元素级截图，非整页/非固定像素坐标）
   ▼
写库（复用 record-competitor-snapshot.ts 的 service-role 直连模式）
   │  上传图片 → competitor-shots 存储桶
   │  插入一行 competitor_shots（shot_on=当天日期，tag='live_auto'）
   ▼
异常处理
      CDP 连不上 / 找不到对应 tab / 页面出现验证码类异常
        → 记本地日志 + 发 macOS 系统通知，提醒人工介入
        → 本次窗口跳过，不重试（避免短时间内反复触发风控）
      截图成功
        → 静默入库，不主动通知（与现有每日指标打点行为一致）
```

## 4. 组件清单

| 组件 | 说明 |
| --- | --- |
| `scripts/live-watch/config.json`（新增） | 每账号：`handle` / `competitor_id` / 当天的 4-6 个时间窗口（本地时间段） |
| launchd plist（新增） | 高频（如每 3-5 分钟）唤醒 runner |
| runner 脚本（新增） | 判断当前时刻落在哪些账号窗口内，逐账号发起检查 |
| CDP 检查逻辑（新增） | 连接用户专用 Chrome 实例，按 URL 匹配 tab，读在播状态 + 截图 |
| 本地状态文件（新增） | 每账号记「最近一次检查是否在播」，用于判断场次跳变 |
| 写库脚本（复用/扩展现有模式） | 沿用 `scripts/record-competitor-snapshot.ts` 的 service-role 直连、上传桶+插表模式 |
| `competitors` 建档（数据准备） | 补 `nexgen1021` 一条记录 |

**不需要改动数据库 schema**——`competitor_shots` 表已有 `image_url` / `shot_on` / `tag` 字段，直接复用；场次去重靠本地状态文件，不需要额外的 room_id 字段落库。

## 5. 待确认 / 尚未拍板的点

1. **专用 Chrome 实例（带 `--remote-debugging-port`）的启动方式**：由用户手动维护（写个启动脚本/alias 自己执行），还是也要把这一步纳入自动化（比如开机自启）？—— 讨论中尚未拍板。
2. **直播画面容器的截图选择器**：需要在实现阶段对着真实页面 DOM 结构摸出来（用浏览器工具实测），当前只确认了截图范围 = 整个直播画面容器（TikTok 播放器叠加的横幅/礼物飘屏/秀场菜单等都算画面的一部分，不是要单独拼接的区域）。
3. **失败通知的具体形式**：已确认方向是「macOS 本地通知 + 本地日志」，通知文案/日志格式待实现时定。

## 6. 非目标（明确排除）

- 直播间实时互动数据（弹幕、礼物流水、在线人数曲线等）—— 沿用竞品监测既有的「非目标」边界
- 24 小时无差别高频轮询 —— 用户明确不要
- 云端/服务器常驻部署 —— 明确要求本地 Mac 方案
- 自动打开/维护浏览器 tab 本身（登录、暂停播放）—— 人工职责
